## Problem Statement

llm-wiki-skill already has a complete knowledge management workflow (init/ingest/batch-ingest/query/digest/lint/status/graph), but has obvious shortfalls in the following areas:

1. **Lack of directional context** — wiki has no "goal" declaration; LLM lacks research direction guidance during ingest/query
2. **Single-step ingest quality bottleneck** — a single LLM call does both analysis and generation, they interfere with each other
3. **No deduplication mechanism** — batch-ingest repeatedly processes already-digested material, wasting tokens
4. **No delete workflow** — materials can only be added, not deleted; no data lifecycle management

The competitor nashsu/llm_wiki (Tauri desktop app) has mature solutions in all four of these directions; we can borrow its core ideas and adapt them to the skill architecture.

## What Makes This Cool

These changes turn the wiki from "passive piling" into "a directional, maintainable knowledge system". purpose.md gives each operation a compass, two-step ingest makes analysis quality leap, caching eliminates waste, and delete lets the knowledge base breathe. The four changes combined will visibly raise the system's professionalism.

## Constraints

- All changes at the SKILL.md + shell script layer; no new runtime framework introduced
- Does not affect backward compatibility of existing wikis (new features are optional add-on capabilities)
- SHA256 cache stored locally in the wiki (`.wiki-cache.json`), no external database
- Cascade delete joins SKILL.md as the new 9th workflow (delete)

## Premises

1. **SKILL.md is an executable spec** — changing SKILL.md is changing the product; changing scripts is just changing infrastructure. User agreed.
2. **purpose.md is a pure addition** — old wikis without purpose.md aren't affected in any function; new wiki init generates template. User agreed.
3. **Two-step ingest changes the flow description** — the core is a restructuring of SKILL.md's ingest workflow, script unchanged. User agreed.
4. **SHA256 cache local storage** — `.wiki-cache.json` placed at wiki root, structure simple and readable. User agreed.
5. **delete is an independent workflow** — doesn't couple with existing workflows, user-actively triggered. User agreed.

## Approaches Considered

### Approach A: Do all four at once (recommended)

Implement all four improvements at once, because they're interrelated:
- init modification simultaneously adds purpose.md and cache initialization
- ingest refactoring naturally integrates two-step flow + cache read/write
- delete completes the lifecycle

**Effort:** M
**Risk:** Medium (ingest is the core workflow, modified by both improvement 2 and improvement 3, need to carefully arrange change order)
**Pros:**
- Modify SKILL.md once, avoiding multiple refactorings of the same area
- Four changes mutually verify, design consistency is good
- Tests can be written together

**Cons:**
- Single diff is larger, needs careful review
- ingest workflow is simultaneously modified by two-step flow and cache check, interaction effects need verification

### Approach B: P0+P1 first, P2+P3 later

First do purpose.md and two-step ingest (the two highest-value items), cache and delete later.

**Effort:** S (first batch)
**Risk:** Low
**Pros:**
- Fastest to get core value
- Two-step ingest is the biggest single-point improvement

**Cons:**
- batch-ingest redundant-waste problem persists
- Data lifecycle incomplete

### Approach C: Each item independent commit

Four changes each independent commit, only change one aspect each time.

**Effort:** M
**Risk:** Low
**Pros:**
- Each change minimized, easiest to review
- Small rollback scope when problems occur

**Cons:**
- SKILL.md gets edited repeatedly, merge risk each time
- init/ingest related changes spread across multiple commits, poor overall coherence

**RECOMMENDATION:** Approach A. All four changes are in the same file (SKILL.md) in the core area (init, ingest, new delete); splitting them actually increases the cost of repeated editing.

## Improvement 1: purpose.md — directional context

### Change content

**1. New template files** `templates/purpose-template.md` (Chinese) and `templates/purpose-en-template.md` (English):

```markdown
# Research Purpose and Direction

## Core Goal
<!-- What problem does this knowledge base solve? Who does it help? -->
[to fill]

## Key Questions
<!-- The 3-5 questions you most want to know answers to -->
1. [to fill]
2. [to fill]
3. [to fill]

## Research Scope
<!-- Which domains/topics are covered? What's not covered? -->
**Covers:** [to fill]
**Does not cover:** [to fill]
```

**2. SKILL.md init workflow modification:**
- After creating the directory structure, additionally generate `purpose.md`
- Prompt user to fill in core goal and key questions
- Stored at same level as `.wiki-schema.md`

**3. SKILL.md ingest workflow modification (initial scope):**
- In the "read context" step, explicitly include reading `purpose.md`
- Priority: `purpose.md` > `.wiki-schema.md` > `index.md`
- ingest uses purpose.md to guide entity/topic classification and weighting
- **purpose.md integration into query and digest is a later enhancement**, verify value after user has actually filled in purpose.md (YAGNI)

**4. wiki-compat.sh modification:**
- Old wikis without purpose.md aren't affected (backward compatibility)
- status workflow reports whether purpose.md exists

### Why it works

Currently each ingest, the LLM only knows "what the topic is" (from `.wiki-schema.md`), not "why the user built this wiki". purpose.md supplements "why" and "where to go", making the LLM's classification, selection, and summarization more targeted.

## Improvement 2: Two-step chain-of-thought ingest

### Current flow (single step)

```
URL/file → extract content → [one LLM call] → generate all wiki pages
```

One call requires the LLM to simultaneously analyze (extract entities, recognize concepts, find contradictions) and generate (write pages, update index); the two tasks compete for attention.

### New flow (two step)

```
URL/file → extract content → [Step 1: analysis] → [Step 2: generation] → write to file
```

**Step 1 — structured analysis:**
Input: raw content + purpose.md + existing wiki structure (index.md summary)
Output: JSON-formatted analysis result
```json
{
  "source_summary": "one-sentence summary",
  "entities": [{"name": "xxx", "type": "person|concept|tool|org", "relevance": "high|medium|low"}],
  "topics": [{"name": "xxx", "importance": "high|medium|low"}],
  "connections": [{"from": "xxx", "to": "xxx", "type": "contrast|cause|association"}],
  "contradictions": [{"claim_a": "...", "claim_b": "...", "context": "..."}],
  "new_vs_existing": {"new_entities": [...], "updates": [...]}
}
```

**Step 2 — page generation:**
Input: raw content + purpose.md + Step 1's analysis result + existing related wiki pages
Output: content for all wiki pages that need to be created/updated

### SKILL.md changes

ingest workflow splits into two steps:
- **Long content (>1000 chars)**: goes through two-step flow, Step 1 analysis + Step 2 generation. Step 1 replaces the original "read material, extract key info" step; Step 2 replaces the original "generate material summary page" through "update log" steps.
- **Short content (<=1000 chars)**: keep simplified flow unchanged (not worth the token cost of two steps)
- Step 1 analysis result isn't persisted (used and discarded), only passed within the same ingest flow
- **Fault tolerance design:** If Step 1 output isn't valid JSON, or missing required fields (entities, topics), auto fall back to single-step flow. Don't block the entire ingest due to format issues.

### Why it works

Analysis task needs "reading and thinking"; generation task needs "writing and organizing". After splitting, Step 1 focuses on understanding, Step 2 takes the structured analysis result and focuses on expression. This matches the human process of writing a review: first read through and take notes, then start writing.

## Improvement 3: SHA256 incremental cache

### Design

**Cache file:** `.wiki-cache.json`, stored at wiki root

```json
{
  "version": 1,
  "entries": {
    "raw/articles/2024-01-15-ai-article.md": {
      "hash": "sha256:abc123...",
      "ingested_at": "2024-01-15T10:30:00Z",
      "source_page": "wiki/sources/2024-01-15-ai-article.md"
    }
  }
}
```

**Key computation:** `sha256(file relative path + file content)` — hash path+content together to avoid false matches for same-name different-content.

### Script changes

Add `scripts/cache.sh`, providing three subcommands:
- `check <file>` — returns `HIT` (already cached and source_page exists) or `MISS` (needs processing). On HIT, additionally verify the source_page file is still on disk (it may have been cascade-deleted); if not, degrade to MISS
- `update <file> <source_page>` — write cache after processing. hash is auto-computed internally by `cache.sh update` via `sha256(relative path + file content)`; caller only needs to pass `<file>` and `<source_page>`
- `invalidate <file>` — delete the cache entry (for force reprocess or cleanup after cascade delete)

### SKILL.md changes

- **ingest workflow:** After "extract content", before "LLM processing", add cache check. HIT → skip LLM call, directly read existing wiki page. MISS → normally go through two-step flow; update cache after completion. Cache HIT semantics is optimistic lock: assumes wiki state is consistent with last processing. If wiki pages were manually edited or cascade-deleted in between, cache may be stale. `cache.sh check` verifies source_page file still exists; if not, degrade to MISS.
- **batch-ingest workflow:** For each file first `cache check`, only process MISS files. After completion, report stats: `Skipped N (unchanged), processed M (new/updated)`.
- **delete workflow:** When deleting material, `cache invalidate` the corresponding entry.
- **init workflow:** Initialize empty `.wiki-cache.json` when creating wiki.

### Backward compatibility

- Old wikis without `.wiki-cache.json`: all files are MISS (equivalent to no cache)
- wiki-compat.sh detects and reports cache status

### Why it works

batch-ingest of 10 files, 7 of which haven't changed. Without cache, we'd spend 7 full LLM calls' worth of tokens for nothing. With cache, only process the 3 that actually changed.

## Improvement 4: Cascade delete (delete workflow)

### Design

Add the 9th workflow: `delete`.

**Trigger words:** "delete source", "remove", "删除素材", "移除"

### Flow

```
User specifies material → confirm scope → cascade cleanup → update cache
```

**Step 1 — Identify target:**
User says "delete that AI article"; LLM searches in `raw/` for matching files, shows found files for user confirmation.

**Step 2 — Analyze impact scope (script search + LLM decision):**
Reference scanning is done by script (no LLM, guarantees full precision); decision by LLM.

Script search logic (add `scripts/delete-helper.sh` or integrate into `cache.sh`):
```bash
# Search all wiki pages containing that material's filename
grep -rl "material_filename" wiki/ --include="*.md"
# Search pages whose sources: frontmatter contains that material
grep -rl "sources:.*material_filename" wiki/ --include="*.md"
# Search pages whose [source: ...](...) links point to that material
grep -rl "\[source:.*\](.*material_filename.*)" wiki/ --include="*.md"
```

After LLM gets the file list returned by script, it judges page by page whether to delete or modify (keep page, only remove reference).

**Step 3 — Cascade cleanup:**

| Cleanup item | Rule |
|--------|------|
| raw/ original file | Delete |
| wiki/sources/ corresponding page | Delete |
| wiki/entities/ entities referencing this material | Keep page, delete reference paragraphs for this material (locate via frontmatter `sources:` or inline `[source:](...)` links. If source attribution can't be determined, keep content). If the entity is only referenced by this one material, prompt user whether to also delete the entity page |
| wiki/topics/ topics referencing this material | Same entity rule |
| wiki/comparisons/ comparisons referencing this material | Same entity rule |
| wiki/synthesis/ syntheses referencing this material | Same entity rule |
| wiki/index.md | Delete entries related to this material |
| wiki/log.md | Add a delete operation log |
| wiki/overview.md | Mark as needing regeneration |
| [[wikilinks]] dead links | Use grep script to scan all pages, clean links pointing to deleted pages |
| .wiki-cache.json | Delete corresponding entry |

**Step 4 — Report:**
```
Deleted:
  - raw/articles/2024-01-15-ai-article.md
  - wiki/sources/2024-01-15-ai-article.md
Updated (references removed):
  - wiki/entities/AI-Agent.md
  - wiki/topics/大语言模型.md
Needs regeneration:
  - wiki/overview.md
```

### Safety mechanisms

- **Confirmation step:** When impact exceeds 5 pages, list all affected pages for second confirmation
- **Don't auto-delete standalone entities:** If an entity is referenced by multiple materials, only delete references, not pages
- **Reversibility hint:** Inform user "if you need to recover, you can re-ingest from raw/"

### Workflow routing table update

Add a row to SKILL.md's workflow routing table:
```
| '删除素材', 'remove', 'delete source', '移除' | -> **delete** |
```

## Improvement 5: Confidence labeling

### Source

Borrowed from graphify's confidence labeling system. graphify labels each graph relation with EXTRACTED/INFERRED/AMBIGUOUS, letting users know which are facts and which are guesses.

### Design

In the two-step ingest's Step 1 analysis result, add a confidence label to each entity relation and connection:

- **EXTRACTED** — Fact directly extracted from source (e.g., "Zhang San is the CEO of the company" appears in the original text)
- **INFERRED** — Relation the LLM inferred based on context (e.g., inferring two concepts are related based on multiple articles)
- **AMBIGUOUS** — Relation the LLM is uncertain about, needs later verification
- **UNVERIFIED** — Degradation mode only (see fault tolerance design)

### SKILL.md changes

In the two-step ingest's Step 1 JSON output format, add a confidence field to entities and connections. **confidence is a required field**, same level as entities and topics; missing it triggers fallback:
```json
{
  "entities": [{"name": "xxx", "type": "concept", "relevance": "high", "confidence": "EXTRACTED"}],
  "connections": [{"from": "A", "to": "B", "type": "cause", "confidence": "INFERRED"}]
}
```

In generated wiki pages, INFERRED and AMBIGUOUS relations are labeled with HTML comments:
```markdown
<!-- confidence: INFERRED -->
There's a causal relation between A and B...
<!-- confidence: AMBIGUOUS -->
These two may be related, needs verification...
```

**Degradation scenario handling:** When Step 1 JSON format abnormality triggers single-step fallback, all generated content is uniformly labeled as `<!-- confidence: UNVERIFIED -->`, and a comment is added at the top of the page explaining this processing was degraded due to format issues. No inconsistent state of "some labeled, some not".

lint workflow adds confidence report: counts each type of confidence, highlights AMBIGUOUS entries for user verification. Adds audit logic: sample-check whether entries labeled EXTRACTED can be found verbatim in the original material, preventing LLM from overestimating certainty.

### Why it works

A wiki without confidence labeling, users can't tell which are facts extracted from original text and which are AI guesses. With labels, users can targetedly verify uncertain content, improving overall credibility of the knowledge base.

## Improvement 6: Query result persistence (memory feedback loop)

### Source

Borrowed from graphify's memory feedback loop. graphify saves Q&A results back into the knowledge base, merging them on next processing.

### Design

Add a step at the end of query workflow: save the synthesized answer as `wiki/queries/{date}-{topic}.md`.

Page format (note `derived: true` marker):
```markdown
---
type: query
derived: true
title: "Synthesized answer about XXX"
created: 2024-01-15
updated: 2024-01-15
tags: [topic1, topic2]
sources: ["source1.md", "source2.md"]
related: ["entity1", "entity2"]
---

## Question
User's original question

## Answer
LLM-generated synthesized answer

## Cited sources
- [source: ...](../sources/xxx.md)
```

### Self-reference protection (critical)

Query pages are LLM-synthesized secondary artifacts, not first-hand material. To prevent self-reference inflation loops:

1. **Secondary source marker:** `derived: true` in frontmatter explicitly identifies this as derived content
2. **ingest downweight:** During two-step ingest's Step 1 analysis, query pages are treated as secondary sources; relevance is auto-downweighted. Not used as primary knowledge source
3. **Confidence linkage:** Info originating from query pages is uniformly labeled as `INFERRED` in newly generated pages, even if the query page originally labeled it EXTRACTED
4. **Don't auto-include:** ingest flow doesn't actively scan `wiki/queries/` directory. Only when the LLM actively judges it's needed when analyzing existing wiki structure does it read it

### Duplicate detection

Before query persistence, first search under `wiki/queries/` for existing pages on the same topic (match via frontmatter tags and title):
- If existing, prompt user whether to update the existing page (replace old version, old moved to `superseded-by` marker) or create new page
- Filename uses `{date}-{short-hash}` rather than pure topic, avoiding naming conflicts

### SKILL.md changes

- At end of query workflow: if the answer cited synthesized analysis from 3+ sources, prompt user "save this answer to the knowledge base?" (use a specific count rule rather than vague "high value" judgment)
- After user confirmation, run duplicate detection, generate query page per template
- Update index.md to add new entry

### Why it works

Answers to common questions accumulate; the knowledge base evolves from "material warehouse" into a "living knowledge system". The secondary source marker and downweight processing prevent the inflation problem of the LLM citing its own synthesized results as first-hand facts.

## Improvement 7: Auto-inject Wiki context

### Source

Borrowed from graphify's hook pattern and claude-mem plugin's SessionStart pattern.

### Phase 0 verification result

The original design used PreToolUse hook + `Grep|Glob|Read` matcher + echo plain text output. Verification results:

1. **echo plain text isn't seen by LLM** — hook output must be structured JSON (`{"systemMessage": "..."}` or `{"hookSpecificOutput": {"additionalContext": "..."}}`); plain text is like talking to air
2. **PreToolUse triggers on every tool call** — fires dozens of times in a typical session; injecting reminders each time is noise bombing
3. **Conclusion: PreToolUse isn't suitable for this scenario**

### New solution: SessionStart hook

Switch to **SessionStart hook**. Triggers once at each session start, injecting wiki path info via `hookSpecificOutput.additionalContext`.

### Platform support status

| Platform | Hook support | Solution |
|------|----------|------|
| Claude Code | SessionStart hook (verified feasible) | Register hook, call script to output JSON |
| Codex | Doesn't support SessionStart hook | Inject wiki context hint at start of AGENTS.md |
| OpenClaw | Internal hook mechanism (incompatible) | Not supported for now |

### Design

**Claude Code platform:**

Modify `~/.claude/settings.json`, register SessionStart hook:

```json
{
  "hooks": {
    "SessionStart": [{
      "hooks": [{
        "type": "command",
        "command": "bash ~/.claude/skills/llm-wiki/scripts/hook-session-start.sh"
      }]
    }]
  }
}
```

Add `scripts/hook-session-start.sh`:
```bash
#!/usr/bin/env bash
# SessionStart hook: inject wiki context at session start (triggers only once)
WIKI_PATH=""
[ -f ~/.llm-wiki-path ] && WIKI_PATH=$(cat ~/.llm-wiki-path)

# Try current directory
if [ -z "$WIKI_PATH" ] && [ -f .wiki-schema.md ]; then
  WIKI_PATH="$(pwd)"
fi

# No wiki, silently return empty JSON
[ -z "$WIKI_PATH" ] && echo '{}' && exit 0
[ ! -f "$WIKI_PATH/.wiki-schema.md" ] && echo '{}' && exit 0

# Inject via additionalContext (LLM will see this text)
printf '{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"[llm-wiki] Detected knowledge base: %s/index.md; consult wiki content for context when answering questions"}}\n' "$WIKI_PATH"
```

**Codex platform:**
On skill install, append a line to the project's `AGENTS.md`:
```
<!-- llm-wiki context: If a knowledge base exists, first consult wiki/index.md -->
```

### settings.json safety mechanism

- **Backup:** Before modification, copy to `settings.json.bak.llm-wiki`
- **Idempotent:** Use `jq` to check if hook already exists (match by command string); skip if already exists
- **Merge:** Use `jq` for array append rather than overwrite, preserving user's existing other hooks
- **Rollback:** Provide `--uninstall-hooks` flag to remove llm-wiki's hook entry from settings.json

### install.sh behavior

- `install.sh --platform claude` — no hook registered by default
- `install.sh --platform claude --install-hooks` — after skill install, register SessionStart hook
- `install.sh --install-hooks` (skill already installed) — only register hook, don't reinstall skill files
- `install.sh --uninstall-hooks` — remove hook (delete llm-wiki entry from settings.json)

### Why it works

Currently users must actively say "check wiki for X" to trigger the knowledge base. SessionStart hook reminds once at each session start, not noisy or fussy; the AI agent naturally consults the wiki when needed. Quieter by dozens of times than PreToolUse.
